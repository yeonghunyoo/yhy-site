## Overview

handoff-agent (2026.09 ~ · Claude Code Plugin · Python MCP) is a plugin based on Claude Design's handoff package that implements three platforms—iOS, Android, and backend—simultaneously.

The starting question: If everything is already decided, why not develop all three platforms at once? And if those "decisions" are refined outputs expressed in numerical values, can we guarantee implementation consistency simply by having agents translate them into their respective languages?

## Plugin Composition

- Built MCP servers for design refinement, backend infrastructure spec interviews, and intermediate artifact management.
- Intermediate artifacts are generated in platform-specific languages (e.g., Swift, Kotlin) and passed to the agents.
- A Python-based MCP proposes and assembles OpenAPI-based backend specs to generate documentation.
- Three agents: Platform (iOS, Android, backend).

## Workflow

1. Design — Create app design prototypes using Claude Design.
2. Screen Refinement — Refine HTML screens into per-screen layout trees, text, icons, and transition tables.
3. Server Infrastructure — Interview regarding topic, features, and expected scale to select infrastructure configuration.
4. API Contract — Define app and server APIs based on the data required by the screens.
5. Common File Generation — Deliver API definitions, design tokens, text, and icons as files.
6. Development & Verification — Three agents develop the code; a program verifies consistency, and once a human approves, the code is merged.

## Case Study 1: Designing Rules for UI/UX Implementation Consistency

Problem: The HTML exported by Claude Design was a browser-based prototype, containing too much unrefined data to pass directly to implementation agents.

- Five screens were merged into a single 917-line file using state branching.
- All formatting was inline (166 styles, 0 classes), meaning there was no concept of reusable components.
- Prototype decorations not present in actual apps were mixed in (fake status bars, home indicators, smartphone frames, runtime JS).

Approach: Markdown-based "prose" soft guides struggle to produce consistent results. Instead, I generate quantified documents and artifacts through a code-based pipeline, allowing agents to develop autonomously based on these outputs. Each agent has access to platform development knowledge and the intermediate artifacts produced by the pipeline.

## Implementation 1: handoff Package Refinement — HTML → Layout Tree → Native

The same elements (gap 20, text, color, behavior) are transferred from HTML → Tree → SwiftUI/Compose. The example shows the header of the Forest home screen.

- ① Claude Design HTML (design/project/forest.dc.html): Flex column with inline style (gap:20px), title "forest", greeting, and settings button.
- ② Server-generated Layout Tree (design/derived/layout/home.json): kind: column · gap: 20px, text: Strings.Home.forest, color: DesignTokens.Color.Accent._300, button: on_click openSettings.
- ③ SwiftUI implemented by iOS agent (HomeView.swift): VStack(spacing: 20), Text(Strings.Home.forest), Palette.accent300, Button(action: model.openSettings).
- ④ Compose implemented by Android agent (HomeScreen.kt): Column(Arrangement.spacedBy(20.dp)), Text(Strings.Home.forest), Palette.accent300, IconButton(onClick = model::openSettings).

## Refinement Results in Numbers

The goal of refinement is consistency verification. I transform what humans used to compare visually into quantifiable metrics that programs can count.

- Structure: One 917-line file → 4 per-screen trees (320, 242, 150, 103 lines).
- Colors: 119 literals → 0.
- Naming: Text · Icons · Behavior → 80 text items · 10 icons · 25 handlers · 31 components.
- Prototype decorations not present in the app (fake status bars, home indicators, phone frames, runtime JS) are excluded from the tree.
- The playing screen is classified as `type: modal` overlay, resulting in 4 trees — the extractor treats overlays as components rather than separate screens.

## Implementation 2: Server Generates Common Resources as Platform Constant Files

The same content is generated side-by-side in Swift and Kotlin within `shared/generated/` (e.g., `Strings.swift`, `Strings.kt`, "generated by the server; never edit"). Similarly, `ApiRoutes`, `Screens`, `DesignTokens`, and `Icons` are also generated in both languages.

## Result: Performance Verification — Comparison Before and After Handoff Package Refinement

The cost incurred by the agent to create the same screen decreased, and the output became closer to the design. Measured 8 times for iOS and 8 times for Android (16 times total).

| | Original HTML (57KB) | Refined Layout Tree |
| --- | --- | --- |
| Tokens (Avg) | 90.5k | 55.1k (−39%) |
| Screen Fidelity | Out of 8 runs with this input, 7 times the screen changed arbitrarily — conditional areas were always displayed, and random colors were used instead of specified ones | The only omissions were attributes not included in the tree by the extractor → subsequently improved to a lossless method that includes all style attributes |

I compared the results by having the same model implement the same screen while only changing the input. Since fidelity is the priority when a design is finalized, I chose to adopt the refined tree.

## Case Study 2: Creating Backend Infrastructure Specification Documents

Problem: Backend infrastructure configuration is variable depending on key features, expected user scale, budget, etc., which felt cumbersome; an interview process was needed to assist this. This was also to identify user needs and avoid excessive server configurations.

Approach: The agent proposes an appropriate infrastructure combination in an easy-to-read table based on features and interviews, and the user either selects a predefined combination or discusses freely to configure the backend specification.

Implementation — A 4-step infrastructure decision interview, where each step must be completed before moving to the next:

1. Stack — Narrow down and select from 2–3 candidates for platform and backend language.
2. Scale — User enters approximate expected MAU · DAU.
3. Filtering Candidates — Out of 12 combinations, only 5 matching that scale remain.
4. Pricing Lookup — Reads only the official pricing pages. Fetched fresh every time without caching.

## API Specification Generation

Once the infrastructure is determined, the system reads the screen HTML and development documents, extracts endpoints from the data required by each screen, and generates an `openapi.yaml` draft. The design handoff package determines the scope of the design.

Example of the forest API draft: It only contains the data required by the 4 design screens (onboarding · home · sound · stats) and shared components. Scope not created due to absence in design:

- No Login/Signup screens → Create an account via anonymous device registration and issue a JWT (POST `/auth/device`, `registerDevice`).
- No extended music browsing UI → Provide only the catalog and download URLs.
- No payment/subscription purchase screens → Subscription status is read-only; management and history are redirected to external links.

Once the interview is complete, a summary table is provided to the user in the session before moving to the next step.

When backend modifications are required after implementation, or if modifications are made arbitrarily, a process of submitting a report to the user was established — it was determined that it is more efficient for the agent to complete the loop quickly and summarize the changes to trigger the next loop, rather than letting the agent decide arbitrarily and looping multiple times. Reason for the report: Since the agent's autonomy creates differences, it is difficult to strictly enforce everything, and it is natural that additional requirements may arise even if written according to the design.

## Case Study 3: Premise for Public Deployment — Not Leaking Secrets into the Pipeline

Problem: Environments where API keys and sensitive information could be exposed to cloud sessions and public repositories — once read, they are loaded into the context and remain in the repository history.

Implementation: Manage sensitive values only via environment variables to prevent direct exposure of values, and use hooks to block direct access to files containing sensitive values.

Result: 0 secrets read by the LLM during development, and 0 secrets in the public repository of the generated project — values were handled exclusively through environment variables. Once the builder agents produce the output, the user is guided to manually input actual sensitive information (certificates, keys, etc.).

Examples of Agent Guidance:

- REPLACE_WITH_D1_DATABASE_ID in wrangler.toml → Replace with the actual ID created via `npx wrangler d1 create forest`
- JWT_SECRET is only added as a Worker secret → `npx wrangler secret put JWT_SECRET` (32+ bytes random) → Only a placeholder remains in the repository
- Apply remote migration before deployment → `npx wrangler d1 migrations apply forest --remote`
