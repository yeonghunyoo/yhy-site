# 로드맵 제안: 동영상과 자동 분류

상태: **제안 (구현 전)**. 2026-11-04 작성. 동영상의 세부 결정은 "동영상 세부 결정", 분류 쪽 정할 것은 맨 아래에 있습니다. 웹·모바일별 업로드·다운로드 규칙은 [platform-policy.md](platform-policy.md).

전제는 지금 설계와 같습니다.
- 처리는 기기에서 합니다. 웹은 브라우저(Web Worker), 모바일 앱은 OS 기본 기능입니다 ([platform-policy.md](platform-policy.md)). 서버 변환 컨테이너는 쓰지 않습니다.
- 클라우드 업로드는 선택 구독(개인 10GB) 안에서 합니다 ([service-plan.md](service-plan.md), 11/04 재조정). 지금 코드는 아직 서비스 전체 8GB 상한입니다 ([mvp.md](mvp.md) "현재 용량 한도").

## 핵심 방향: 원본은 기기에, 가족에게는 가벼운 사본을

동영상은 사진보다 훨씬 큽니다. iPhone 4K로 1분을 찍으면 약 350MB라서, 개인 10GB는 동영상 30개가 안 돼서 찹니다.

- **기기 동영상 (PC 폴더, 휴대폰 사진첩):** 사진처럼 올리지 않고 nuvo 뷰어에서 바로 재생합니다. 원가는 0원이고 구독이 필요 없습니다.
- **가족과 나눌 동영상 (구독자):** 기기가 720p로 압축한 **공유용 사본만** 올립니다. 1분에 약 15MB이고, 원본은 PC에 남깁니다.

## 1. 동영상 수집과 자체 뷰어

### 수집 (이 PC 폴더)
| 기능 | 방법 |
|---|---|
| 동영상 찾기 | 폴더 스캔 대상에 mp4, mov, m4v 등 추가 |
| 정보 읽기 | 파일 전체를 읽지 않고 앞부분만 분석해서 촬영 시각, 위치, 길이, 해상도, 코덱을 뽑음 (mp4box.js 등, Web Worker에서 실행) |
| 대표 화면 | 영상 10% 지점의 장면을 썸네일로 저장 |
| 미리보기 줄 | 장면 10개 정도를 한 장으로 이어 붙여 저장. 마우스를 올리면 장면이 넘어감 |
| 빠른 식별 | 큰 파일 전체 해시는 느림. "크기 + 앞뒤 1MB 해시"로 먼저 식별하고, 업로드할 때만 전체 sha256 계산 |
| Live Photo | iPhone의 HEIC + 짧은 MOV 쌍을 하나로 묶어 "움직이는 사진"으로 표시. 안드로이드 모션 포토(JPEG 안의 MP4)도 꺼냄 |

### 자체 뷰어
- 타임라인에서 사진과 함께 보여주고, 동영상에는 재생 아이콘과 길이를 표시합니다.
- 마우스를 올리면 미리보기가 재생되고, 클릭하면 전체 화면 플레이어가 열립니다.
- 플레이어 기능: 탐색 막대 위 장면 미리보기, 재생 속도, 한 프레임씩 넘기기, 키보드 단축키, 사진과 같은 좌우 넘김
- 재생할 수 없는 형식(MKV, AVI, 일부 HEVC)은 대표 화면과 "다른 앱으로 열기"를 보여줍니다.
  - HEVC 재생 여부는 기기와 브라우저마다 다르므로 실기기 확인이 필요합니다.

### 공유용 업로드 (Space)
| 문제 | 해법 |
|---|---|
| 용량 | 브라우저 동영상 인코더(WebCodecs)로 720p, 약 2Mbps 사본을 만들어 올림. 서버 변환 비용 없음 |
| Worker 요청 크기 100MB 제한 | ~~R2 분할 업로드(multipart)~~ → 11/04 검토: 길이 제한 안의 사본은 100MB 아래라 **지금의 단일 업로드를 그대로 씀**. 아래 V3 |
| 재생 중 건너뛰기 | `/m/*` 미디어 경로에 구간 요청(Range) 지원 추가 |
| 용량 한도 | 동영상도 개인 10GB에 포함. 길이 제한(예: 3분) 권장 — 720p·2Mbps 3분은 약 45MB라 지금의 100MB 단일 업로드 안에 들어감 |

## 동영상 세부 결정 (11/04 검토)

지금 코드(`worker/routes/uploads.ts`, `worker/routes/media.ts`, `@nuvo/shared`)와 대조한 결과입니다. 각 항목의 "제안"은 정해지기 전 기본값이고, `[ ]`가 정할 것입니다.

### V1. 클라우드에 올리는 범위
- 제안: **공유용 사본만** 올립니다. 원본은 기기에 남깁니다.
- [ ] 사본만 (제안) / 원본도 선택 가능 / 동영상은 안 올림

### V2. 사본 화질과 길이
- 제안: 720p, 영상 약 2Mbps, 소리 AAC 128kbps, 길이 **최대 3분**. 3분이면 약 45MB입니다.
- 더 길면 앞 3분만 올리는 대신 업로드를 막고 안내합니다. 잘린 영상이 원본처럼 보이면 안 되기 때문입니다.
- [ ] 화질 (720p 제안 / 1080p)
- [ ] 최대 길이 (3분 제안). 100MB 단일 업로드 안에 들어가려면 720p·2Mbps 기준 약 6분이 한계입니다.

### V3. 업로드 방식: 단일 업로드 유지, multipart 보류
- 지금 업로드는 `MEDIA.put(..., { sha256 })`으로 R2가 내용과 해시가 맞는지 검증합니다. 그 뒤에 업로드 영수증(HMAC)을 발급하고 내용 주소(`o/{sha256}`)로 저장합니다. [mvp.md](mvp.md) "보안 설계"의 "해시와 내용이 다른 업로드는 거부"가 이 구조에 기대고 있습니다.
- R2 multipart는 파일 전체 sha256을 검증하지 않습니다. 쓰려면 내용 주소와 영수증 모델을 바꿔야 합니다.
- 결론(제안): V2 길이 제한으로 100MB 아래를 지키고, **단일 업로드를 유지**합니다. multipart는 원본 업로드나 긴 영상이 필요해질 때 보안 모델과 함께 다시 설계합니다.
- [ ] 이 방향 확정

### V4. 원본과 사본 연결
- 압축은 매번 결과가 조금씩 달라서, 사본의 sha256은 원본과 다르고 같은 영상을 두 번 압축해도 다릅니다.
- 지금 sha256 하나로 하는 일 중에 이것들이 깨집니다.
  - 타임라인 "같은 사진은 한 칸"
  - 백업 여부 확인
  - 중복 건너뛰기
  - 이미 있는 사진에 연결(link)
- 제안: `assets`에 **원본 해시 칼럼**(`source_sha256`)을 둡니다. 사진은 비워 두거나 자기 해시를 넣습니다. 동영상은 사본을 만든 원본의 해시를 넣습니다. 기기와 nuvo를 맞출 때와 중복 확인은 이 칼럼으로 합니다.
- 원본 해시는 서버가 검증할 수 없습니다(원본이 서버에 없음). 그래서 사용자가 접근할 수 있는 라이브러리 안에서만 비교에 씁니다. 남의 사진 존재 여부를 알 수 없다는 지금 규칙을 그대로 지킵니다.
- [ ] 칼럼 이름과 위치 (`assets.source_sha256` 제안)
- [ ] 다른 멤버가 같은 원본으로 만든 사본이 이미 있을 때: 연결(link)로 처리 (제안) / 새로 올림

### V5. 빠른 식별과 전체 해시
- 기기 동영상은 전체 sha256 계산이 느립니다(4K 1분 350MB).
- 제안: 화면에 보여 줄 때는 "크기 + 앞뒤 1MB 해시"(빠른 식별)를 씁니다. 사본을 올릴 때만 원본 전체 sha256을 계산해서 V4 칼럼에 넣습니다.
- 타임라인 합치기는 지금처럼 전체 sha256 기준입니다. 원본 해시를 아직 계산하지 않은 기기 동영상은 합쳐지지 않은 채로 보입니다.
- 휴대폰의 같은 사진 판정 기준은 [service-plan.md](service-plan.md) "정할 것"과 함께 정합니다.
- [ ] 빠른 식별 방식 (크기 + 앞뒤 1MB 제안)

### V6. 데이터 모델 변경
| 변경 | 내용 (제안) |
|---|---|
| `assets.kind` | `photo` / `video` / `live` |
| `assets.duration_ms` | 동영상 길이 |
| `assets.source_sha256` | V4 |
| Live Photo | 사진 1장에 파일 2개. `assets.motion_blob_id`(짧은 영상 Blob)로 둘째 파일을 연결. 용량은 두 파일 합 |
| 썸네일 종류 | 지금 `512`·`2048`에 대표 화면(`poster`)과 미리보기 줄(`strip`) 추가. 미디어 경로가 받는 종류(`o`·`512`·`2048`)도 넓힘 |
| 허용 형식 | `SUPPORTED_MIME`에 `video/mp4` 추가 (사본은 항상 mp4로 만듦) |

- [ ] Live Photo를 `motion_blob_id`로 둘지, 별도 `asset_parts` 표로 둘지 (앞쪽 제안)

### V7. 재생 서빙
- 지금 `/m/*`는 구간 요청(Range)을 지원하지 않습니다. 동영상 탐색에 필요합니다.
- 제안: R2 `get`의 range 옵션으로 206 응답을 줍니다. 엣지 캐시에는 전체 파일을 넣고, 구간 요청은 캐시에서 잘라서 줍니다.
- 서명 URL 만료(6~12시간)는 동영상에도 충분합니다.
- 미디어 응답의 CSP·`nosniff`는 그대로 둡니다. `<video>`로 재생할 때는 응답 CSP가 재생을 막지 않습니다.
- [ ] 엣지 캐시에 동영상을 넣을지 (제안: 넣음, 사진과 같은 하루)

### V8. 재생할 수 없는 형식
- 제안: 대표 화면과 "다른 앱으로 열기"를 보여줍니다(위 "자체 뷰어"와 같음). 사본을 만들 수 있으면 "공유용 사본 만들기"도 같이 보여줍니다.
- HEVC 재생 여부는 기기와 브라우저마다 다르므로 실기기에서 확인합니다.

### V9. 사본 만드는 도구
- 웹: 분해(mp4box.js) → 디코딩·인코딩(WebCodecs) → **다시 묶기**(mp4 muxer 라이브러리, 하나 골라야 함). 소리도 인코딩해야 합니다. Safari의 오디오 인코딩 지원은 실기기로 확인합니다.
- 모바일 앱: OS 기본 인코더(iOS AVFoundation, Android Media3)를 씁니다 ([platform-policy.md](platform-policy.md) "동영상").
- [ ] 웹 다시 묶기 라이브러리 선택
- [ ] 웹에서 인코딩을 못 하는 브라우저: 업로드 막고 웹 PC·앱 안내 (제안)

### V10. 용량 계산
- 사본 크기와 대표 화면·미리보기 줄을 개인 10GB에 넣습니다. 지금 썸네일 몫 12%는 사진 기준이라, 동영상은 실제 크기로 셉니다.
- [ ] 동영상 썸네일 몫 계산 방식 (실제 크기 제안)

### V11. 순서
1. 기기 동영상 보기: 웹 PC 먼저, 모바일 앱은 앱 1단계에서 ([service-plan.md](service-plan.md) "순서 제안")
2. 데이터 모델(V6) + Range 서빙(V7)

## 2. 중복 자동 분류 (지금 기능 확장)

지금은 완전히 같은 파일(sha256)과, 크기를 바꾸거나 다시 압축한 사진(dHash)을 찾습니다. 여기에 다음을 더합니다.

| 묶음 | 판단 기준 | 제안 |
|---|---|---|
| 연속 촬영 | 같은 카메라, 몇 초 안에 찍힘, 모양이 비슷함 (dHash) | 가장 선명한 1장 추천 (선명도 점수). "23묶음 정리하면 1.2GB 절약" |
| 카톡으로 받은 사본 | 촬영 정보 없음, 해상도 낮음, 원본과 모양이 같음, 파일 이름 `KakaoTalk_` | 원본이 있으면 사본 정리 제안 |
| 동영상 중복 | 길이가 ±0.5초 안에서 같고, 장면 8개의 모양이 일치 | 다시 압축한 영상과 메신저로 받은 영상을 찾아 고화질본을 남김 |
| 스크린샷·저장 이미지 | 파일 이름, 촬영 정보 없음, 화면 해상도와 일치 | "추억 아님" 칸으로 분리 |

**원칙: 자동으로 지우지 않습니다.** "정리 제안함"에 모으고, 사용자가 확인한 뒤에 정리합니다.
그러려면 **휴지통(30일 보관)이 먼저 필요합니다** (지금은 즉시 삭제).

## 3. 카테고리 자동 분류 (비용이 낮은 순서)

### 1단계: 규칙 기반 (0원)
- **사진 종류:** 스크린샷, 셀카(전면 카메라 정보), 파노라마(가로세로 비율), 연사, Live Photo, 동영상, 슬로모션, 타임랩스, 편집본
- **이벤트 묶음:** 촬영 시각이 6시간 이상 끊기는 지점과 위치 변화로 나눕니다. 예: "2026년 5월 · 제주 · 3일 · 412장"
- **여행 감지:** 가장 자주 찍힌 위치를 "집"으로 보고, 집에서 먼 묶음을 여행으로 표시합니다.
- **지명 붙이기:** 외부 API 없이 한국 시·군·구 경계 데이터를 앱에 넣어 브라우저에서 찾습니다. 비용이 없고 위치가 밖으로 나가지 않습니다.

### 2단계: 기기 안에서 도는 AI (0원, 사진이 밖으로 나가지 않음)
- 이미지와 문장을 함께 이해하는 소형 모델(CLIP 계열)을 브라우저에서 실행합니다 (WebGPU, ONNX Runtime Web 또는 Transformers.js).
- 썸네일(512px)마다 특징 벡터를 한 번 계산해 두면 다음이 가능합니다.
  - **카테고리:** 음식, 바다, 산, 아기, 반려동물, 문서·영수증, 생일·케이크 등 미리 정한 목록으로 분류
  - **문장 검색:** "눈 오는 날 아이", "할머니 생신". 한국어 검색은 다국어 모델이 필요해서 모델 선택이 중요합니다.
  - **비슷한 사진:** dHash보다 정확한 유사 묶음
- 저장 위치
  - 이 PC 사진: IndexedDB
  - 클라우드 사진: Postgres(Neon) pgvector. int8로 압축하면 사진 한 장에 약 0.5KB
- 비용: 모델을 처음 한 번 내려받습니다 (수십~100MB대). 처리 속도는 기기마다 크게 다르고 10만 장이면 몇 시간이 걸릴 수 있어서, 쉬는 시간에 이어서 처리하도록 만듭니다.

### 3단계: 나중에
- **얼굴 묶기:** 생체정보라 별도 동의와 법률 검토가 필요합니다 ([developer-guide.md](developer-guide.md) 14단계).
- **서버 AI** (Workers AI 등): 비용이 생기므로 유료 플랜 이후 검토합니다.

카테고리는 사진에 태그를 박아 넣지 않고 **계산해서 보여주는 스마트 앨범**으로 만듭니다.
사용자가 고친 결과만 저장하면, 모델을 바꿔도 다시 계산하면 됩니다.
