# nuvo 결정 기록

프로젝트의 **왜**를 남기는 문서입니다. 무엇을 정했는지뿐 아니라 **어떤 선택지를 봤고, 무엇을 버렸고, 어떤 자료를 근거로 했는지**를 적습니다. 나중에 "그때 왜 이렇게 했지"를 코드나 채팅 기록을 뒤지지 않고 여기서 찾습니다.

**규칙**
- 결정·잠정·제안이 생기거나 바뀔 때마다 아래에 **덧붙입니다**(위에 새 항목). 지우지 않고, 뒤집히면 새 항목에서 "D-00N을 뒤집음"이라고 씁니다
- 한 항목 = 날짜 · 상태(확정/잠정/제안) · 결정 · 본 선택지 · 이유 · 자료(출처·조사·계산) · 관련 문서
- 세부 수치·표는 해당 설계 문서에 두고 여기서는 링크합니다. 이 문서는 요약과 이유입니다
- 사소한 구현 선택은 코드 주석·커밋 메시지로 충분합니다. 여기 적는 건 **제품·정책·구조·돈**에 관한 것

상태 표시: **확정** = 그대로 진행 / **잠정** = 이 기준으로 진행하되 바뀔 수 있음 / **제안** = 기본값일 뿐 아직 결정 아님

### D-013 · 제안 · 구독 가격 후보 A ₩2,900 / B ₩1,900 / C ₩3,900+30GB
- 상태: **미결정**. A를 제안
- 계산: 고정비 월 ≈ ₩48,000(Workers $5, Neon ≈ $20, Apple $99/연, 도메인), 변동비 구독자당 월 ≈ ₩250(10GB 꽉 채움, R2 저장+요청). 수취액 = 표시가 ÷ 1.1(부가세) × 0.85(수수료). 손익분기 ₩1,900→40명, ₩2,900→25명, ₩3,900→18명
- 본 것: 용량 단가로는 iCloud 50GB ₩1,100·MYBOX 80GB·Google One 100GB ₩2,400·M365 100GB ₩2,900에 10배 이상 밀림. 가장 가까운 상품은 FamilyAlbum(한 명 결제, 가족 전체) 가족 ₩5,900·1인 ₩2,900
- 이유(A): 손익분기와 시장 기준 사이에서 설명이 쉽고 위아래 조정 여지가 남음. "10GB가 작다" 반응이 오면 가격을 내리기보다 용량을 올리는 쪽이 싸다(변동비가 수취액의 10%)
- 자료: [pricing.md](pricing.md) 전체

### D-011 · 확정 · 초대받은 가족은 구독 없이 Space 보기
- 본 것: 구독 없이는 로컬 보기만(D-007) / 초대받은 가족도 각자 구독 / 작은 체험 용량
- 이유: 휴대폰에는 이미 사진 앱이 있어 "로컬 보기만"은 쓸 이유가 약함. 돈 내는 사람 한 명, 보는 사람 여럿이 가족 서비스 구조에 맞음(FamilyAlbum과 같은 구조)
- 남은 것: 구독 없는 가족이 **올리기**도 되는지(제안: 가능), Space 용량은 누구 몫인지(제안: 소유자 10GB), 소유자가 해지하면(제안: 보기 유지·올리기만 막음)
- 문서: [service-plan.md](service-plan.md) 기능 구분·정할 것

### D-010 · 확정 · 결제는 앱 스토어에서만, 웹은 앱 설치 안내
- 본 것: ① 웹 PG + Android 소비 전용(앱은 로그인만) + iOS IAP ② 웹 PG만, iOS 앱은 로컬 뷰어만 ③ **앱 스토어만**(iOS IAP + Google Play 결제), 웹 결제 없음
- 버린 이유: ①은 PG·Apple 두 결제 수단을 합쳐야 하고 iOS에선 웹 구독 조회만 해도 IAP가 필수(3.1.3(b))라 복잡함이 줄지 않음. ②는 iOS 앱의 쓸모가 거의 없어짐
- 고른 이유: 결제 수단이 스토어로 통일돼 PG 계약·빌링키 관리가 없어지고, 제품 중심이 모바일(D-009)이라 자연스러움. 웹은 스토어 규칙 밖이라 "앱에서 구독하세요" 안내가 자유
- 대가: Android도 Play 결제 연동이 필수가 됨(앱 안에서 팔기 때문). 모든 매출에 수수료 15%
- 자료: Apple 심사 3.1.1·3.1.3(a)(b)·4.8, Google Play 결제 정책·FAQ(소비 전용 정의) — [media-security.md](media-security.md) 3.4·4.5
- 문서: [service-plan.md](service-plan.md) 결제 구조, [platform-policy.md](platform-policy.md) 7

### D-009 · 확정 · 제품 중심은 모바일 앱, 웹은 확장. 개발은 웹(서버) 먼저
- 본 것: 웹 중심(PC 폴더 보기가 핵심) / 모바일 중심
- 이유: 사진은 휴대폰에서 찍히니 백업·공유도 거기서 일어남. PC는 큰 화면 감상·관리. 다만 계정 이전·용량·구독 상태·약관·신고 기능은 전부 서버 일이라 **개발 순서는 웹 먼저**, 앱은 그걸 그대로 씀
- 순서: 1차 웹(서버) → 2차 모바일(Capacitor, IAP·Play 결제, 백업) → 3차 동영상·분류
- 문서: [service-plan.md](service-plan.md) 목표·순서

### D-008 · 제안 · 이미지·동영상 보안 정책 (공통·웹·iOS·Android)
- 핵심 발견: 지금 코드는 **원본 EXIF(위치)를 그대로 저장하고 Space로 보낼 때 lat/lng도 복사** — 위치가 의도 없이 공유되는 것을 막는 장치가 없음
- 제안: Space로 보낼 때 DB 위치 복사 안 함 / E2E 암호화 안 함(공유·썸네일·분류가 서버에서 읽어야 함) / 업로드 매직 넘버 검사 / 화면 캡처 차단 안 함 / Space 다운로드는 editor 이상 / SPA에 script-src CSP
- OS 조사로 드러난 스토어 공통 필수: **사진 신고·멤버 차단·공개 연락처·약관 동의**(UGC 정책, 가족 비공개 Space도 대상). iOS: Sign in with Apple 필수(4.8), Precise Location 신고. Android: 사진 권한 선언 폼, `ACCESS_MEDIA_LOCATION` 첫 출시 제외 제안, 웹 계정 삭제 페이지, WorkManager
- 자료: Apple 심사 가이드라인(2026-10-16 개정), PhotoKit 문서, Play Console 도움말 원문 — URL은 문서 안
- 문서: [media-security.md](media-security.md)

### D-006 · 제안 · 동영상: 공유용 720p 사본만, 단일 업로드 유지, 원본 해시로 연결
- 본 것: R2 multipart 업로드 / 원본 업로드 / 서버 변환
- 버린 이유: multipart는 R2의 sha256 검증을 못 쓰고, 그 검증 위에 업로드 영수증(HMAC)과 내용 주소 저장이 서 있음. 720p·2Mbps 3분이 약 45MB라 지금의 100MB 단일 업로드로 충분
- 핵심 설계: 압축 사본은 원본과 해시가 달라 타임라인 합치기·중복·연결이 깨짐 → `assets.source_sha256`으로 원본 해시 연결
- 상태: 세부 V1~V11이 제안. 3차 단계에서 확정
- 문서: [roadmap-video-classification.md](roadmap-video-classification.md) "동영상 세부 결정"
